cos2pag

Automatise la réplication d'un bucket IBM Cloud Object Storage vers PoINT Archival Gateway, orchestrée par PoINT Data Replicator — CTIE.
Résumé Workflow Référence API

01Résumé

Pour un bucket COS donné, cos2pag met en place — et maintient — toute la chaîne de réplication vers l'archivage sur bande via PAG, sans intervention manuelle sur les trois systèmes :

Sur COS : ajoute le compte de service de sauvegarde à l'ACL du bucket, ajoute l'IP de PDR à la liste blanche du firewall, et configure le topic de notification du bucket.

Sur PAG : crée la partition du tenant si elle n'existe pas encore (avec sa configuration de buffer persistant), crée ou met à jour le repository du bucket, active le versioning d'objets, et applique une politique de cycle de vie (suppression des uploads multipart incomplets, expiration des versions, suppression des marqueurs de suppression expirés).

Sur PDR : crée ou met à jour la tâche de réplication (source S3 = COS, cible S3 = PAG), avec planning et notifications Kafka, puis lance une copie initiale complète si la tâche vient d'être créée — sans quoi les objets déjà présents avant la mise en place ne seraient jamais copiés.

  • IdempotentRelancer l'outil sur un bucket déjà configuré ne republie rien : chaque étape compare l'état réel avant d'agir et ressort SKIPPED/OK si rien ne diffère.
  • Tenant toujours explicite--tenant est obligatoire en ligne de commande, jamais deviné du nom du bucket — des codes tenant réels comme ME, ME-SR, ME-SRE se chevauchent, deviner risquerait de se tromper silencieusement.
  • Lifecycle via l'API S3L'onglet « Rules » de PAG n'est pas exposé par l'API REST d'administration documentée (il passe par un formulaire interne à session/CSRF) — cos2pag applique donc les mêmes règles via l'API S3 standard de PAG, sur son port S3 dédié.
  • Planning réparti le week-endpdr.schedule.weekend_spread assigne à chaque bucket un créneau différent (par défaut toutes les 2h, samedi et dimanche), calculé de façon déterministe à partir du nom du bucket, pour éviter que toutes les copies hebdomadaires démarrent au même instant.

02Workflow

Une exécution traite un seul bucket et touche quatre systèmes dans l'ordre, chacun avec ses propres appels API :

Lecture (GET) — toujours exécutée Écriture (POST/PATCH/PUT) — seulement si un changement est nécessaire
